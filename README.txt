# Telco Customer Churn: прогноз оттока и выбор порога для retention-кампании

End-to-end ML-проект: от бизнес-постановки до расчёта ожидаемой прибыли retention-кампании. Сравниваются 5 моделей, выбирается порог контакта по критерию максимума прибыли, а не по accuracy.

## 1. Бизнес-задача

Телеком-оператор теряет клиентов. Бюджет на удержание ограничен: менеджеры могут обзвонить или дать скидку только части клиентов. Задача — **не «предсказать отток ради accuracy»**, а **отранжировать клиентов по вероятности оттока и выбрать порог контакта, при котором кампания приносит максимум ожидаемой прибыли**.

Пусть для клиента с вероятностью оттока `p`:
- `C` — стоимость одного контакта/скидки,
- `L` — прибыль, если клиента удалось удержать,
- `s` — вероятность, что кампания сработает.

Ожидаемая прибыль от контакта: `p · s · L − C`. Контактим, если это выражение > 0, то есть при `p > C / (s · L)`.

## 2. Данные

**Датасет:** [Telco Customer Churn](https://www.kaggle.com/datasets/blastchar/telco-customer-churn) (IBM / Kaggle).

- 7 043 клиента, 19 признаков + целевая `Churn`
- Доля оттока: **26.54%** (классы несбалансированы → accuracy бесполезна)
- Целевая переменная: `Churn = 1`, если клиент ушёл

**Предобработка:**
- `customerID` удалён как не несущий информации;
- `TotalCharges` хранится как `object`, содержит скрытые пропуски `" "` — приведён к `numeric` через `pd.to_numeric(errors="coerce")`, пропуски импутированы медианой;
- Числовые признаки: `SeniorCitizen`, `tenure`, `MonthlyCharges`, `TotalCharges`;
- Категориальные: 15 признаков (`Contract`, `PaymentMethod`, `InternetService` и др.) — One-Hot Encoding с `handle_unknown="ignore"`;
- Всё препроцессинг внутри `sklearn.Pipeline`, обучается только на train-фолдах — **leakage исключён**.

## 3. Подход

**Валидация:**
- Train/test split 80/20, `stratify=y`, `random_state=42`.
- 5-fold `StratifiedKFold` на train для честного сравнения моделей.

**Модели:**
| Модель | Комментарий |
|---|---|
| `DummyClassifier (prior)` | Baseline: «всегда большинство» |
| `LogisticRegression` | `class_weight="balanced"`, `max_iter=2000` |
| `DecisionTreeClassifier` | `max_depth=5`, `class_weight="balanced"` |
| `RandomForestClassifier` | 200 деревьев, `class_weight="balanced"` |
| `HistGradientBoostingClassifier` | 300 итераций, `learning_rate=0.05` |

**Метрика выбора:** **PR-AUC** (average precision) — устойчивее к дисбалансу классов, чем ROC-AUC.

**Выбор порога:**
1. **Аналитический** по бизнес-допущениям: `C=50, s=0.30, L=500` → `p > 0.333`.
2. **Эмпирический** — sweep порога 0.05…0.95 по OOF-предсказаниям (out-of-fold), выбор по максимуму ожидаемой прибыли.

## 4. Результаты

### Сравнение моделей (5-fold CV на train)

| Модель | CV ROC-AUC | CV PR-AUC |
|---|---:|---:|
| **LogReg** | **0.8455** | **0.6569** |
| HistGradientBoosting | 0.8324 | 0.6366 |
| DecisionTree (depth=5) | 0.8264 | 0.6221 |
| RandomForest (200) | 0.8222 | 0.6080 |
| Dummy (prior) | 0.4999 | 0.2653 |

**Победитель — LogisticRegression.** Несмотря на простоту, она обогнала бустинг по PR-AUC. Причина: сигнал в данных в основном линейный (тип контракта, tenure, способ оплаты), а бустинг на 7 тыс. строк с balanced-весами переобучается. Плюс LogReg интерпретируема — коэффициенты читаются бизнесом.

### Метрики на test (1409 клиентов, 374 ушедших)

| Порог | ROC-AUC | PR-AUC | Precision | Recall | F1 | Accuracy | Контактов |
|---|---:|---:|---:|---:|---:|---:|---:|
| 0.50 | 0.8413 | 0.6326 | 0.5043 | 0.7834 | 0.6136 | 0.7381 | 581 |
| 0.333 (аналит.) | 0.8413 | 0.6326 | 0.4413 | 0.9144 | 0.5953 | 0.6700 | 775 |
| **0.60 (эмпир.)** | 0.8413 | 0.6326 | **0.5399** | **0.7059** | **0.6118** | **0.7622** | **489** |

### Бизнес-эффект на test

Допущения: `C = 50`, `L = 500`, `s = 0.30`.

| Стратегия | Ожидаемая прибыль |
|---|---:|
| Никого не контактить | 0 |
| Контактить всех | **−14 350** (убыток) |
| Модель @ 0.333 (аналит.) | +12 550 |
| **Модель @ 0.60 (эмпир.)** | **+15 150** |

**Вывод:** «контактить всех» — убыточно, потому что средний отток 26.5%, ниже точки окупаемости кампании. Модель с эмпирическим порогом приносит **на 29 500 больше**, чем контакт всех клиентов, и экономит 286 контактов по сравнению с аналитическим порогом.

### Почему эмпирический порог (0.60) выше аналитического (0.333)

`class_weight="balanced"` компенсирует дисбаланс классов, умножая вес положительного класса примерно в 2.8 раза. Из-за этого **предсказанные вероятности завышены**: «0.4» от такой модели в реальной шкале ближе к 0.15. Аналитический порог `C / (s·L) = 0.333` корректен только для калиброванных вероятностей, поэтому на практике его нужно сдвигать вверх — что и делает эмпирический sweep по OOF-предсказаниям.

## 5. Ограничения

- **Бизнес-допущения `C`, `L`, `s` — гипотезы.** В реальной компании они уточняются у финансового отдела; порог чувствителен к ним (при `s=0.15` прибыль сжимается, при `s=0.5` — растёт).
- **Вероятности не откалиброваны.** Для продакшена стоит добавить `CalibratedClassifierCV(isotonic)` и перепроверить оптимальный порог — калиброванная модель позволит использовать аналитический порог осмысленно.
- **Кампания моделируется упрощённо:** один контакт = одинаковый эффект, нет учёта канала (звонок vs email), нет стоимости по сегментам.
- **Данные исторические**, датасет 2019–2020 гг.; на живых данных может потребоваться retraining и проверка на дрейф.
- **Нет uplift-моделирования.** Модель предсказывает вероятность оттока, а не эффект от кампании. В идеале — обучать две модели: `P(уйдёт | не контактили)` и `P(уйдёт | контактили)`, и контактить тех, у кого эффект максимальный.
